# 0205 — The backend deploys to the new server through one switch and one forced command
- **Date:** 2026-10-04
- **Status:** decided (built on `invotick-apis` branch `feat/deploy-to-new-server`, not merged, not deployed; nothing in production changes until the switch is flipped)
- **Decision:** CI picks the server with ONE project variable, `DEPLOY_TARGET`: `old` (the default, the path that has always run, unchanged), `new` (one call to the new server as a deploy-only user), `hold` (nothing deploys, pipeline orange). Any other value fails before anything is built.
- **Why:** the owner moves production to a new box (migration plan 2026-10-02). The deploy has to be able to follow, but a deploy that goes wrong must be impossible by default: a pipeline with no variable must still do what it did yesterday, a typo must not pick a server, and the key CI holds for the new box must not be a root key to a shared machine.
- **What `new` does:** `tar` of exactly `compose.yml` + `well-known/assetlinks.json` piped to `ssh deploy-invotick@HOST "deploy <short-sha>"`. The forced command on the box (`/usr/local/sbin/deploy-invotick`) checks the compose file against a policy, pulls the tag with the box's own read-only registry login, starts it, waits for `/actuator/health/deploy`, and puts the previous tag back on failure. CI never sends a secret (env file and Firebase/Play files live in `/srv/invotick/secrets`), never runs Docker on the box, and refuses to deploy a commit that is no longer the head of `stage`.
- **Rejected:**
  - *A second pipeline file or a branch for the new server* — two things to keep in step; the switch is one variable on the same pipeline.
  - *`new` as the default, or "any value that is not `old` means `new`"* — a missing or mistyped variable would then choose the new box. Unknown values fail loudly instead.
  - *Root over ssh to the new box, as the old job does* — the old job's key is a root key and it copies secrets on every run. The audit's finding 2.
  - *Shipping the monitoring configs in the same tar* — the server's script accepts only `compose.yml` and `well-known/`; widening a forced command to more files is a larger permission than this deploy needs. Cost accepted: monitoring config changes no longer reach the box from CI (see Consequences).
  - *A public health probe from CI after deploy* — until DNS moves, `stage.invotick.com` still names the OLD box; the probe would judge the wrong server. The script checks 127.0.0.1 on the box.
  - *Swap beyond the limit, and `docker update` for limits* — a container that outgrows its limit is restarted (`unless-stopped`, `memswap_limit` = `mem_limit`) and the Health Centre says so; limits live in the compose files that ship.
- **Consequences:**
  - New CI variables, names only: `DEPLOY_TARGET`, `DEPLOY_HOST`, `DEPLOY_SSH_KEY` (File, Protected, environment `production`), `DEPLOY_KNOWN_HOSTS`. The owner creates them; they are listed in `invotick-apis/deploy/README.md`.
  - Open: **changes to `prometheus.yml`, `loki-config.yml`, `promtail-config.yml` and `grafana/` no longer reach the box by merging.** Decision 0077's retention lives in one of them. They have to be installed by hand (or the script widened, which is its own decision).
  - New Health Centre card, "Container memory vs limit" (peak over 6 h, kills in 24 h), because the limits are estimates from one week on the old box and a limit kills rather than slows.
  - The cutover order for the switch: `hold` from T-1, `new` after the box serves production, `old` only after the reverse cutover has put the data back.
  - Found while reading the server's Caddy files (other branch, `ops/vps-n/edge/available/invotick.caddy`): `handle /.well-known/assetlinks.json { root * /srv/edge/well-known; file_server }` looks for `…/well-known/.well-known/assetlinks.json` and answers 404 (tested on Caddy 2.11). It needs `rewrite * /assetlinks.json` before `file_server`. Android's App Links check reads a 404 there as "this site does not vouch for the app".
